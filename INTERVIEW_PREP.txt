PATIENT-TRIAGE 
================================================

This document consolidates the technical interview explanation for the main
triage endpoint and supporting services:

1. backend/app/api/endpoints/triage.py
2. backend/app/services/assessment_engine.py
3. backend/app/services/rag_engine.py
4. backend/app/services/routing_engine.py
5. backend/app/middleware/pii_scrubber.py
6. backend/scripts/train_triage_model.py


PART 1: backend/app/api/endpoints/triage.py
============================================

30-SECOND INTERVIEW SUMMARY
---------------------------

triage.py exposes a FastAPI POST /evaluate endpoint. It receives patient
information, validates it through Pydantic, removes identifiable information
from the complaint, determines which age-specific triage route should be used,
optionally retrieves matching EHR history using the patient MRN, and sends the
combined data to the assessment engine.

The assessment engine combines:

- XGBoost numerical prediction
- LLM interpretation of the complaint and history
- Confidence calculation
- Deterministic clinical-risk badges

The endpoint then returns the recommended ESI score, confidence, rationale,
model-routing information, and a small history snippet.


1. TriageRequest: input contract
---------------------------------

The request model is:

class TriageRequest(BaseModel):
    mrn: Optional[str] = None
    name: str
    age: Optional[float] = None
    dob: Optional[str] = None
    complaint: str
    hr: Optional[int] = None
    bpSys: Optional[int] = None
    bpDia: Optional[int] = None
    spo2: Optional[int] = None
    temp: Optional[float] = None
    pain: Optional[int] = None

Required fields:

- name
- complaint

Optional fields:

- Medical record number: mrn
- Age and date of birth
- Heart rate
- Blood pressure
- Oxygen saturation
- Temperature
- Pain score

This is a Pydantic request model. FastAPI automatically validates incoming
JSON against it.

Example valid request:

{
  "mrn": "MRN-A3F9",
  "name": "John Doe",
  "age": 68,
  "complaint": "Chest pain and shortness of breath",
  "hr": 110,
  "bpSys": 170,
  "bpDia": 95,
  "spo2": 91,
  "temp": 37.4,
  "pain": 8
}

If name or complaint is missing, FastAPI rejects the request before
evaluate_patient() executes and normally returns HTTP 422.

Interview answer:

"TriageRequest acts as the API boundary. It gives us structured, typed input
instead of accepting an unvalidated dictionary. FastAPI and Pydantic handle
validation automatically."


2. /evaluate endpoint
----------------------

The route is:

@router.post("/evaluate")
async def evaluate_patient(request: TriageRequest):

This defines a POST endpoint.

The endpoint is asynchronous from FastAPI's perspective, but the functions
called inside it are mostly synchronous:

- scrub_pii(...)
- route_patient_payload(...)
- retrieve_patient_history(...)
- execute_triage_assessment(...)

Interview point:

"The endpoint is defined as async, but if the downstream services perform
blocking work, they should either be made async or moved to a thread or
background worker in a high-concurrency production system."


3. Step 1: PII scrubbing
------------------------

The endpoint first executes:

safe_complaint = scrub_pii(request.complaint, request.name)

The scrubber removes the supplied patient name and phone-like values from the
complaint before downstream AI processing.

Example:

Raw:
John Doe called 555-123-4567 reporting chest pain

Scrubbed:
[PATIENT_NAME] called [PHONE] reporting chest pain

The cleaned complaint is used before sending data to the LLM.

Fail-closed behavior:

If the scrubber crashes, it does not return the original text. It returns:

[SYSTEM ERROR: PII SCRUBBER FAILED. TEXT WITHHELD FOR HIPAA COMPLIANCE.]

This is called fail-closed design.

Interview explanation:

"PII scrubbing is a privacy boundary. If it cannot guarantee that the
complaint is safe, it withholds the content instead of accidentally exposing
raw patient information to the AI model."

Important limitation:

The scrubber currently handles:

- Explicit patient name
- Phone-number-like values

It does not currently implement comprehensive detection for every possible PII
type such as all addresses, email addresses, or arbitrary identifiers.


4. Step 2: routing
------------------

The endpoint converts the validated Pydantic model to a dictionary:

patient_dict = request.model_dump()

Then it routes the patient:

routing_info = route_patient_payload(patient_dict)

The router chooses a route based mainly on age:

- Under 18 -> PEDIATRIC_MODEL
- 18 through 64 -> ADULT_MODEL
- 65 and above -> GERIATRIC_MODEL

It also returns an uncertainty penalty and warning.

Example:

{
  "model_route": "GERIATRIC_MODEL",
  "uncertainty_penalty": 0.0,
  "warning": null
}

If age cannot be calculated, the router attempts to use an estimated age group
and applies a confidence penalty:

{
  "model_route": "ADULT_MODEL",
  "uncertainty_penalty": 0.15,
  "warning": "Age estimated. Clinical baselines may be inaccurate."
}

Interview explanation:

"Routing is a stratification step. Pediatric, adult, and geriatric patients
can have different normal vital-sign ranges, so the system selects a
clinically appropriate model route before assessment."


5. Step 3: RAG retrieval
------------------------

The endpoint initializes:

ehr_history = "NO PRIOR HOSPITAL HISTORY FOUND."

Then it only performs retrieval when an MRN exists:

if request.mrn:
    ehr_history = retrieve_patient_history(request.mrn, safe_complaint)

RAG means Retrieval-Augmented Generation. The system retrieves relevant patient
history from the EHR/vector database and provides that context to the
assessment engine.

The retrieval uses:

1. Semantic similarity based on the scrubbed complaint.
2. An exact MRN metadata filter.

The MRN filter is important because semantic search alone might retrieve
another patient's similar medical note.

If there is no MRN, the endpoint skips EHR retrieval and uses:

NO PRIOR HOSPITAL HISTORY FOUND.


6. Step 4: assessment
---------------------

The endpoint calls:

assessment = execute_triage_assessment(
    patient=patient_dict,
    scrubbed_complaint=safe_complaint,
    ehr_history=ehr_history,
    routing=routing_info
)

The assessment engine combines:

A. XGBoost model:
   Uses numerical features such as age, heart rate, blood pressure, SpO2,
   temperature, pain, and an MRN/history flag.

B. LLM:
   Interprets the complaint and EHR context and proposes a complaint category,
   ESI score, and rationale.

C. Dynamic confidence:
   Adjusts confidence for routing uncertainty, model disagreement, missing
   important vitals, and complaint category.

D. Deterministic badges:
   Generates warnings such as hypoxia, hypertension, hypotension, or
   tachycardia using direct rules rather than LLM output.

Interview explanation:

"The XGBoost model gives a quantitative prediction from structured vitals. The
LLM interprets the free-text complaint and EHR context. The final confidence
score does not blindly trust either one; it considers model disagreement,
missing data, and clinical context."


7. API response
---------------

The endpoint returns:

{
    "status": "success",
    "routing": routing_info,
    "recommended_esi": assessment["recommended_esi"],
    "confidence_score": assessment["confidence_score"],
    "rationale": assessment["rationale"],
    "badges": assessment["badges"],
    "ml_model_esi": assessment["ml_model_esi"],
    "retrieved_history_snippet": (
        ehr_history[:120] + "..."
        if ehr_history != "NO PRIOR HOSPITAL HISTORY FOUND."
        else None
    )
}

Typical response:

{
  "status": "success",
  "routing": {
    "model_route": "GERIATRIC_MODEL",
    "uncertainty_penalty": 0.0,
    "warning": null
  },
  "recommended_esi": 2,
  "confidence_score": 87,
  "rationale": "Chest pain with low oxygen saturation requires urgent evaluation.",
  "badges": [
    {
      "label": "Hypoxia (SpO2 91%)",
      "type": "danger"
    }
  ],
  "ml_model_esi": 3,
  "retrieved_history_snippet": "[DATE: Oct 2024] Discharge Summary..."
}

Important distinction:

- recommended_esi is normally the LLM's final recommendation when the LLM
  succeeds.
- ml_model_esi is the independent XGBoost prediction.
- If the LLM fails, the assessment engine falls back to the ML result.

The EHR is not returned in full. Only the first 120 characters plus "..." are
returned. This reduces unnecessary exposure of sensitive clinical history.


8. Error handling
-----------------

The endpoint wraps the complete flow in:

try:
    ...
except Exception as e:
    raise HTTPException(status_code=500, detail=str(e))

Therefore:

- Validation errors happen before the function and normally return 422.
- Runtime errors inside the flow become HTTP 500.
- The current error message is returned as the response detail.

Underlying services also have fallback behavior:

- PII scrubber failure -> fail-closed withholding message.
- RAG failure -> no-history fallback.
- XGBoost inference failure -> fallback prediction.
- LLM or assessment failure -> ML prediction and fallback rationale.

Production critique:

The broad endpoint-level exception handler is simple, but not ideal because:

1. It catches every exception.
2. It exposes str(e) to the client.
3. It may reveal internal implementation details.
4. It does not distinguish client errors from dependency failures.

A stronger production pattern would log the full exception internally and
return a generic external message:

logger.exception("Triage evaluation failed")
raise HTTPException(
    status_code=500,
    detail="Triage evaluation could not be completed."
)


9. Important route wiring observation
-------------------------------------

The endpoint file defines an APIRouter. The application must register it using
something similar to:

from backend.app.api.endpoints.triage import router as triage_router

app.include_router(triage_router, prefix="/api/triage")

Then the final route would be:

POST /api/triage/evaluate

If include_router() is not called somewhere, defining @router.post("/evaluate")
does not expose the route publicly.


10. Best interview answer for triage.py
---------------------------------------

"The /evaluate endpoint starts with a Pydantic TriageRequest, which validates
the patient payload and ensures required fields such as name and complaint are
present.

First, the complaint is passed through a fail-closed PII scrubber so the
patient's name and phone-like values are removed before AI processing. Next,
the payload is routed to a pediatric, adult, or geriatric model based on age,
with a confidence penalty if age is estimated.

If an MRN exists, the system performs RAG retrieval. It searches semantically
using the scrubbed complaint but hard-filters by MRN, preventing another
patient's history from being retrieved.

The assessment engine then combines an XGBoost prediction from structured
vitals with an LLM interpretation of the complaint and retrieved history. The
confidence score is adjusted for model disagreement, missing high-value
vitals, and routing uncertainty. Deterministic rules generate clinical badges
such as hypoxia or hypotension.

Finally, the API returns the recommended ESI, confidence score, rationale,
routing information, ML prediction, badges, and a truncated history snippet.
Validation errors result in a 422 response, while runtime failures are
converted into a 500 response, with lower-level services using safe fallbacks
where possible."


Common triage.py follow-up questions
-------------------------------------

Q: Why use both XGBoost and an LLM?

A: XGBoost is strong at structured numerical features such as vitals. The LLM
is better at interpreting free-text complaints and contextual EHR information.
Combining both provides numerical prediction plus language understanding.

Q: Why filter RAG by MRN?

A: Semantic similarity alone can retrieve medically similar records from the
wrong patient. The exact MRN metadata filter provides identity isolation.

Q: What happens if the LLM fails?

A: The assessment engine falls back to the XGBoost ESI and returns a fallback
rationale rather than failing silently.

Q: What happens if data is missing?

A: Missing data reduces confidence. The penalty is context-sensitive: missing
blood pressure is more serious for a cardiac complaint, while missing oxygen
saturation is more serious for a respiratory complaint.

Q: Is the endpoint fully production-ready?

A: It has useful safety patterns such as fail-closed PII handling, MRN-filtered
retrieval, deterministic badges, and ML fallback. However, I would improve
exception handling, validate the DOB type, ensure the router is registered,
and avoid blocking synchronous calls inside an async endpoint.


PART 2: backend/app/services/assessment_engine.py
===================================================

Interview-ready overview:

assessment_engine.py is the decision-fusion layer. It combines:

1. A structured-data XGBoost prediction
2. An LLM interpretation of the complaint and EHR history
3. A confidence-adjustment algorithm
4. Deterministic clinical badges
5. Safe fallbacks if the model or LLM fails

The important design idea is:

"XGBoost handles numerical patient data, the LLM handles clinical language and
context, and the confidence engine measures how trustworthy the combined
result is."


1. XGBoost model loading
------------------------

At module startup, the code looks for:

xgboost_triage_model.joblib

The model path is built relative to the service:

MODEL_PATH = os.path.join(
    os.path.dirname(__file__),
    "..",
    "models",
    "xgboost_triage_model.joblib"
)

If the file exists, it is loaded once:

triage_model = joblib.load(MODEL_PATH)

Loading it once is more efficient than loading it for every request.

If loading fails, the error is logged and triage_model remains None. Inference
then uses a controlled fallback instead of crashing the whole application.

Interview answer:

"The model is loaded during application startup and kept in memory, which
avoids repeated disk I/O for each request. If the artifact is missing or
cannot be loaded, the service continues with a controlled fallback."


2. run_real_xgboost_inference()
--------------------------------

The function is:

def run_real_xgboost_inference(patient: Dict[str, Any]) -> Tuple[int, float, float]:

It converts the patient dictionary into the exact numerical feature array
expected by the trained XGBoost model.

It returns:

(predicted_esi, top_class_probability, margin)

Example:

(2, 0.86, 0.41)

means:

- Predicted ESI is 2
- The top class probability is 86%
- The top class is 41 percentage points ahead of the second class


3. Exact eight input features
-----------------------------

The inference vector is:

features = np.array([[
    _get("age", 35.0),
    _get("hr", 75.0),
    _get("bpSys", 120.0),
    _get("bpDia", 80.0),
    _get("spo2", 98.0),
    _get("temp", 37.0),
    _get("pain", 0.0),
    1.0 if patient.get("mrn") else 0.0
]])

The exact order is:

1. age
2. hr
3. bpSys
4. bpDia
5. spo2
6. temp
7. pain
8. MRN/history indicator

Feature table:

Position  Feature    Meaning                         Default
1         age        Patient age                    35.0
2         hr         Heart rate                     75.0
3         bpSys      Systolic blood pressure        120.0
4         bpDia      Diastolic blood pressure       80.0
5         spo2       Oxygen saturation               98.0
6         temp       Temperature                     37.0
7         pain       Pain score                       0.0
8         MRN flag   Whether an MRN exists            1.0/0.0

The final feature is not the MRN string. It is only:

1.0 if patient.get("mrn") else 0.0

Training uses equivalent positions:

age, hr, bp_sys, bp_dia, spo2, temp, pain, has_history

Runtime uses:

age, hr, bpSys, bpDia, spo2, temp, pain, MRN-presence

The names differ because the API uses camelCase, but order and intended
meanings are intended to match.

Why exact order matters:

The model does not know that the first number means age and the second means
heart rate. It only sees numeric columns in fixed positions. If the
application sends heart rate in the age position, the model still produces a
prediction, but it is based on incorrect feature meanings.

Interview answer:

"The eight features are age, heart rate, systolic BP, diastolic BP, SpO2,
temperature, pain score, and a history/MRN indicator. The order must exactly
match training, otherwise the model receives semantically incorrect data."


4. Missing-value defaults
-------------------------

The helper is:

def _get(key, default):
    val = patient.get(key)
    return float(val) if val is not None else default

For example:

_get("spo2", 98.0)

uses the real SpO2 when supplied, or 98.0 when missing.

This prevents None values from entering the NumPy array.

Trade-off:

A default value can look like a real normal measurement. For example, missing
SpO2 becomes 98.0, which is normal. The model itself may therefore treat
missing data as normal data. The confidence engine separately penalizes some
missing fields, but the XGBoost model does not know whether a value was
measured or defaulted.

Interview answer:

"Defaults provide operational robustness, but they can hide missingness from
the model. A stronger design would pass explicit missing-value indicators or
use a preprocessing pipeline that distinguishes measured values from imputed
values."


5. predict_proba()
------------------

The model call is:

probabilities = triage_model.predict_proba(features)[0]

The classifier has five classes. A result may conceptually look like:

[0.05, 0.70, 0.15, 0.08, 0.02]

Each value is the estimated probability for one class, and the values
normally sum to approximately 1.0.

The probabilities are sorted:

sorted_probs = np.sort(probabilities)[::-1]

Example:

[0.70, 0.15, 0.08, 0.05, 0.02]


6. ESI conversion
-----------------

Training stores zero-based classes:

Clinical ESI 1 -> Model class 0
Clinical ESI 2 -> Model class 1
Clinical ESI 3 -> Model class 2
Clinical ESI 4 -> Model class 3
Clinical ESI 5 -> Model class 4

Runtime code:

top_class_idx = int(np.argmax(probabilities))
predicted_esi = top_class_idx + 1

If the highest probability is at index 1:

1 + 1 = 2

The model predicts ESI 2.

Interview answer:

"XGBoost uses zero-based class indexes from 0 to 4. The application adds one
so the API returns the clinical ESI range of 1 to 5."


7. Probability and margin
--------------------------

Top probability:

top_prob = float(sorted_probs[0])

If top_prob is 0.86, the model's strongest class has an estimated probability
of 86 percent.

Margin:

margin = sorted_probs[0] - sorted_probs[1]

If the top two probabilities are 0.86 and 0.20:

margin = 0.86 - 0.20 = 0.66

A high margin means the model clearly prefers one class. A low margin means
the model is uncertain between multiple classes.

Why both matter:

Case A: [0.60, 0.20, 0.20] -> margin 0.40
Case B: [0.60, 0.59, 0.01] -> margin 0.01

Case B is much less decisive even though the top probability is the same.

Interview answer:

"The top probability measures how likely the winning class is. The margin
measures how far ahead it is from the runner-up. The margin helps detect
ambiguous model decisions."


8. XGBoost failure fallback
---------------------------

If the model is unavailable at startup:

if triage_model is None:
    return 4, 0.75, 0.1

This returns:

- ESI 4
- Probability 0.75
- Margin 0.1

If prediction throws an exception:

except Exception as e:
    logger.error(f"XGBoost Inference error: {e}")
    return 4, 0.50, 0.0

This returns:

- ESI 4
- Probability 0.50
- Margin 0.0

Interview explanation:

"The service remains available even if the model artifact or prediction call
fails. However, this is a prototype-style fallback because it returns a fixed
ESI. In a clinical production system, I would make degraded mode explicit and
likely require human review rather than presenting a fixed prediction as a
normal model result."


9. Deterministic badges
-----------------------

Badges are generated by:

generate_deterministic_badges(patient, routing)

They are intentionally not generated by the LLM. This makes high-visibility
clinical warnings predictable and reproducible.

Blood pressure:

if sys < 90:
    Hypotension
elif sys > 160:
    Hypertension

Oxygen saturation:

if spo2 <= 92:
    Hypoxia
elif spo2 >= 95:
    Normal O2

Values from 93 to 94 receive no SpO2 badge.

Heart rate:

Pediatric route:

if hr > 180:
    Pediatric Tachycardia
elif hr < 160:
    Normal Ped HR

Adult/geriatric route:

if hr > 120:
    Tachycardia
elif 60 <= hr <= 100:
    Normal HR

Interview answer:

"Badges are generated with deterministic, age-aware rules so the UI receives
stable clinical indicators. This avoids allowing an LLM to invent or omit
important warning labels."


10. calculate_dynamic_confidence()
----------------------------------

The confidence function returns an integer from 0 to 99:

return max(0, min(99, int(base_confidence)))

It starts with the XGBoost top-class probability and adjusts it.

Step 1: Start from ML probability:

base_confidence = ml_prob * 100.0

If ml_prob is 0.82:

base_confidence = 82

This is not the final confidence.

Step 2: Routing uncertainty:

base_confidence -= routing_penalty * 100

If the penalty is 0.15:

0.15 * 100 = 15

Example:

Initial confidence: 84
Unknown-age penalty: 15
Adjusted confidence: 69

This is a 15-point subtraction, not 15 percent of the remaining confidence.

Step 3: ML versus LLM disagreement:

if llm_esi != ml_esi:
    base_confidence -= 15.0

Example:

ML ESI: 2
LLM ESI: 3

Confidence loses 15 points.

The disagreement does not automatically decide which ESI is correct. It signals
that the case needs more caution.

If they agree:

base_confidence += (margin * 10)

Example:

Base confidence: 80
Margin: 0.60
Agreement bonus: 6
Result before other penalties: 86

The agreement bonus is larger when the XGBoost model has stronger separation
between its top two classes.

Important behavior:

The LLM ESI is normally used as the returned recommended_esi when the LLM
succeeds, even if it disagrees with XGBoost. The implementation detects
disagreement and lowers confidence, but it does not currently apply a formal
tie-breaker or automatically choose the more urgent ESI.

Interview observation:

"The system detects disagreement and lowers confidence, but the LLM's ESI
remains the recommendation. For production triage, I would define an explicit
disagreement policy, such as choosing the more urgent ESI or routing the case
to a clinician."

Step 4: Missing-data penalties:

Cardiac complaint without blood pressure:

if complaint_category == "CARDIAC" and not has_bp:
    base_confidence -= 30

Respiratory complaint without SpO2:

elif complaint_category == "RESPIRATORY" and not has_spo2:
    base_confidence -= 30

Localized trauma:

elif complaint_category == "TRAUMA_LOCALIZED":
    pass

No missing-data penalty is applied by this branch.

Generic complaints:

if not has_bp:
    base_confidence -= 10
if not has_temp:
    base_confidence -= 5

Final clamp:

max(0, min(99, int(base_confidence)))

Interview answer:

"Confidence is context-sensitive. Missing blood pressure is heavily penalized
for cardiac cases, missing SpO2 is heavily penalized for respiratory cases,
and ordinary missing fields receive smaller penalties."


11. LLM prompt and response
---------------------------

The system prompt tells the LLM:

You are an expert ER triage AI. Analyze vitals, complaint, and EHR history.
Respond strictly in JSON format with exactly three keys.

Expected response:

{
  "category": "CARDIAC",
  "esi": 2,
  "rationale": "..."
}

Allowed categories:

- CARDIAC
- TRAUMA_LOCALIZED
- RESPIRATORY
- OTHER

The LLM is instructed to:

- Return an integer ESI from 1 to 5
- Keep the rationale to two sentences
- Keep the rationale under 40 words

The request uses:

response_format={"type": "json_object"}

and:

temperature=0.1

The low temperature reduces randomness and makes the response more
consistent.


12. Model provider selection
----------------------------

The selected model is:

"qwen/qwen3.8-27b" if settings.OPENAI_API_KEY.startswith("gsk_") else "gpt-4o-mini"

The logic assumes:

- A key beginning with gsk_ is a Groq key.
- Groq-compatible requests use the Qwen model.
- Otherwise, the OpenAI-compatible model is gpt-4o-mini.

The client uses:

base_url="https://api.groq.com/openai/v1"

when the key begins with gsk_.

Interview explanation:

"The code uses an OpenAI-compatible client interface but switches the base URL
and model based on the API-key format, allowing either Groq-hosted or
OpenAI-hosted inference."


13. LLM input
-------------

The current user prompt contains:

Vitals: HR {patient.get('hr')}, BP {patient.get('bpSys')},
SpO2 {patient.get('spo2')} | Complaint: {scrubbed_complaint} |
EHR: {ehr_history}

It includes:

- Heart rate
- Systolic blood pressure
- SpO2
- Scrubbed complaint
- Retrieved EHR history

Important implementation observation:

The prompt currently omits:

- Age
- Diastolic blood pressure
- Temperature
- Pain score

Those fields are used by XGBoost but not directly included in this LLM prompt.
A stronger prompt could include all clinically relevant values while still
using the scrubbed complaint.


14. Parsing the LLM response
----------------------------

The response is parsed with:

raw_content = response.choices[0].message.content or "{}"
llm_data = json.loads(raw_content)

Then:

llm_data.get("esi", ml_esi)

uses the LLM ESI if present, otherwise the ML ESI.

And:

llm_data.get("category", "OTHER")

defaults to OTHER if missing.

Final recommendation:

"recommended_esi": llm_data.get("esi", ml_esi)

So:

- Successful LLM response with esi -> use LLM ESI.
- Missing LLM esi -> use ML ESI.
- LLM request or parsing failure -> use ML ESI in the outer fallback.

Important validation limitation:

The code parses JSON but does not explicitly validate:

- esi is an integer
- esi is between 1 and 5
- category is one of the allowed categories
- rationale is a string
- response contains exactly the expected keys

The prompt requests the constraints, but prompts are not validation.

Interview answer:

"The LLM is instructed to return structured JSON, but production code should
still validate the parsed response against a schema before using it."


15. Low-confidence rationale
----------------------------

If confidence is below 80:

if confidence < 80:
    rationale = (
        f"LOW CONFIDENCE ({confidence}%): "
        "Missing vital data or algorithmic disagreement detected. "
        + rationale
    )

This makes uncertainty visible instead of silently returning a low-confidence
recommendation.


16. Successful result
---------------------

The assessment engine returns:

{
    "recommended_esi": ...,
    "confidence_score": ...,
    "rationale": ...,
    "badges": ...,
    "ml_model_esi": ...
}

Example:

{
  "recommended_esi": 2,
  "confidence_score": 78,
  "rationale": "LOW CONFIDENCE (78%): Missing vital data or algorithmic disagreement detected. Hypoxia and chest pain require urgent evaluation.",
  "badges": [
    {
      "label": "Hypoxia (SpO2 91%)",
      "type": "danger"
    }
  ],
  "ml_model_esi": 3
}

This means:

- LLM recommended ESI 2.
- XGBoost predicted ESI 3.
- Confidence was reduced because the systems disagreed.
- Deterministic rules identified hypoxia.


17. LLM/model failure fallback
------------------------------

The LLM request and result-processing block is inside a try/except. If the
provider request, authentication, network connection, JSON parsing, response
structure, confidence calculation, or another operation fails, the code logs
the error and returns:

{
    "recommended_esi": ml_esi,
    "confidence_score": int(ml_prob * 100),
    "rationale": "SYSTEM ERROR: Relying on deterministic XGBoost fallback rules.",
    "badges": generate_deterministic_badges(patient, routing),
    "ml_model_esi": ml_esi
}

Example:

If ML ESI is 3 and ML probability is 0.72, the fallback is:

{
  "recommended_esi": 3,
  "confidence_score": 72,
  "rationale": "SYSTEM ERROR: Relying on deterministic XGBoost fallback rules.",
  "ml_model_esi": 3
}

Important safety observation:

The fallback confidence is simply int(ml_prob * 100). It does not include
normal routing or missing-data penalties. Therefore, fallback confidence may
be higher than the normal context-aware confidence.

A production improvement would calculate fallback confidence using a
safety-aware deterministic policy and expose a degraded-mode flag.

------------------------

        |
        v
Run XGBoost
        |

        +--> Probability margin

19. Strong technical interview answer for assessment_engine.py
---------------------------------------------------------------

"run_real_xgboost_inference() converts the patient object into an eight-value
NumPy feature vector: age, heart rate, systolic BP, diastolic BP, SpO2,
temperature, pain score, and an MRN/history indicator. The order is important
because it must match the order used during training.

The XGBoost classifier uses predict_proba() to return probabilities for five
classes. The highest-probability class is selected using argmax, and one is
added because the model classes are zero-based while ESI is represented from 1
to 5. The top probability becomes the starting confidence, while the
difference between the top two probabilities is used as a certainty margin.

The system then calls an LLM with the scrubbed complaint, selected vitals, and
EHR history. The LLM is constrained to return JSON containing a complaint
category, ESI value, and short rationale.

The confidence engine starts from the XGBoost probability and adjusts it for
uncertain age routing, missing clinically important data, and ML-versus-LLM
disagreement. If both models agree, a small margin-based bonus is applied. If
they disagree, confidence is reduced by 15 points.

The returned ESI normally comes from the LLM when the LLM response is valid,
while the XGBoost ESI is returned separately for transparency. If the LLM
fails or returns invalid JSON, the system falls back to the XGBoost result.

Finally, deterministic rules generate badges for hypotension, hypertension,
hypoxia, and heart-rate abnormalities. These rules are intentionally outside
the LLM so that important visual warnings are predictable and not dependent on
model-generated text."


Assessment follow-up questions
------------------------------

Q: Why not use only the LLM?

A: Structured vital signs are better handled by a numerical model with
repeatable behavior. The LLM adds language and context understanding, but it
should not be the only source of a clinical decision.

Q: Why calculate a margin?

A: A top probability alone does not show how close the second choice was. The
margin measures how decisively the model selected its prediction.

Q: What does disagreement mean?

A: It means the structured-vitals model and language/context model interpreted
the case differently. The system does not automatically resolve that conflict;
it lowers confidence and exposes both predictions.

Q: Which prediction is final?

A: In the current implementation, the LLM's esi becomes recommended_esi when
the LLM succeeds. XGBoost is retained as ml_model_esi. If the LLM fails,
XGBoost becomes the fallback recommendation.

Q: What would you improve?

A: I would validate the LLM response with a Pydantic schema, include all
relevant vitals in the LLM prompt, distinguish missing values from normal
measurements, define an explicit disagreement policy, and expose a degraded
mode flag when the LLM or model fails. I would also replace broad exception
handling with more specific error handling and safer external error messages.


PART 3: backend/app/services/rag_engine.py
============================================

Interview-ready overview:

rag_engine.py implements Retrieval-Augmented Generation for patient history.

Its job is:

1. Store EHR documents in a ChromaDB collection.
2. Search for history semantically related to the current complaint.
3. Restrict results to the current patient using the MRN.
4. Return matching history to the assessment engine.
5. Handle no-history and retrieval-failure cases safely.

The central idea is:

"Use semantic search to find clinically relevant notes, but use an exact MRN
filter to ensure those notes belong to the correct patient."


1. What is RAG?
----------------

RAG means Retrieval-Augmented Generation.

Instead of asking the LLM to assess the patient using only:

Current complaint + current vitals

the system first retrieves relevant patient history:

Current complaint + matching EHR history

Then that history is passed into the assessment prompt.

For example, if the patient currently reports chest pain, the system may
retrieve a previous note mentioning:

- Severe hypertension
- Diabetes
- Prior myocardial infarction
- Medication allergies

The LLM can then consider that context.

Interview answer:

"RAG gives the language model patient-specific context from the EHR instead of
relying only on its general medical knowledge or the current complaint."


2. ChromaDB collection
-----------------------

The module creates:

chroma_client = chromadb.Client()

Then:

ehr_collection = chroma_client.get_or_create_collection(
    name="patient_ehr_history"
)

A ChromaDB collection is similar to a searchable document store designed for
vector or semantic search. It contains document IDs, document text, metadata,
and internally generated embeddings.

Important implementation detail:

The code uses chromadb.Client(), which is typically in-memory. Although
core/config.py defines:

CHROMA_PERSIST_DIRECTORY = "./chroma_data"

rag_engine.py does not use that setting to create a persistent client. Data
may not survive a process restart.

Interview observation:

"The code is structured around ChromaDB, but persistence is not currently wired
to the configured CHROMA_PERSIST_DIRECTORY. In production, I would use a
persistent Chroma client or a managed vector database."


3. Seeding EHR documents
------------------------

The startup path calls:

seed_mock_ehr_data()

from the application lifespan in main.py.

The seed function first checks:

if ehr_collection.count() > 0:
    return

This prevents duplicate insertion during repeated startup in the same
collection.

Mock records:

{
    "id": "doc1",
    "mrn": "MRN-A3F9",
    "text": "[DATE: Oct 2024] Discharge Summary: Severe hypertension, Type 2 diabetes. Prior mild MI in 2022. Allergic to Penicillin."
}

{
    "id": "doc2",
    "mrn": "MRN-A3F9",
    "text": "[DATE: Jan 2021] ER Note: Patient arrived in 3rd trimester of pregnancy. (RESOLVED)"
}

The records are inserted with:

ehr_collection.add(
    ids=[record["id"] for record in mock_records],
    documents=[record["text"] for record in mock_records],
    metadatas=[{"mrn": record["mrn"]} for record in mock_records]
)

Each record has:

- An ID
- Full text
- Metadata containing the patient MRN

The MRN is stored as metadata so it can be used as an exact filter.


4. retrieve_patient_history()
--------------------------------

The function is:

def retrieve_patient_history(mrn: str, complaint: str) -> str:

It receives:

- mrn: patient identity
- complaint: current, already-scrubbed complaint

It returns a string containing relevant EHR notes.

The endpoint calls it only when an MRN exists.


5. The important Chroma query
-----------------------------

The query is:

results = ehr_collection.query(
    query_texts=[complaint],
    n_results=3,
    where={"mrn": mrn}
)

This has two separate conditions.

A. query_texts=[complaint]

This is semantic search. Chroma converts the complaint into an embedding and
compares it with stored document embeddings.

Example complaint:

Patient reports chest pressure and shortness of breath

A stored document saying:

Prior mild MI and severe hypertension

may be considered relevant even if it does not contain the exact phrase
"chest pressure".

Semantic search means:

Find documents with similar meaning.

It is different from exact string search.

B. where={"mrn": mrn}

This is the metadata filter:

Only search documents whose metadata contains this exact MRN.

For mrn = "MRN-A3F9", only records satisfying:

metadata["mrn"] == "MRN-A3F9"

are eligible.

The semantic ranking happens within that filtered patient scope.

Plain-English meaning of the full query:

"Among this specific patient's EHR documents, find the documents that are
semantically most relevant to the current complaint."

It does not mean:

"Find the most similar document in the entire hospital database and then hope
it belongs to the correct patient."


6. Why MRN hard-filtering prevents patient-data mixing
-------------------------------------------------------

Imagine two patients:

Patient A: MRN-A3F9
Patient B: MRN-B7K2

Both have chest pain.

Patient A:
Prior myocardial infarction and severe hypertension

Patient B:
Normal cardiac workup

A semantic search for "chest pain" could find either patient's note.

Without MRN filtering, the vector search could return Patient B's note for
Patient A.

With:

where={"mrn": "MRN-A3F9"}

the search space is restricted first:

Only Patient A's records are eligible.

Then the complaint ranks Patient A's records by relevance.

Conceptually:

All EHR documents
        |
        | exact MRN filter
        v
Only this patient's documents
        |
        | semantic complaint search
        v
Top relevant history for this patient

Interview answer:

"The MRN filter is an identity boundary. Semantic similarity tells us which
note is relevant, but it does not prove which patient the note belongs to. The
exact metadata filter provides that identity guarantee."

Important wording:

The complaint is a soft semantic signal.
The MRN is a hard identity constraint.


7. Why filter before ranking conceptually
------------------------------------------

Safe design:

Filter by patient identity
then rank by clinical relevance

Unsafe design:

Rank all patients by clinical relevance
then hope the result belongs to the correct patient

The Chroma query combines:

query_texts=[complaint]
where={"mrn": mrn}

The MRN excludes other-patient records from consideration.


8. n_results=3
--------------

n_results=3 asks Chroma for up to three relevant documents.

Multiple records may contain different useful information:

- One note may describe medications.
- Another may describe a previous diagnosis.
- Another may contain an allergy or important event.

The returned documents are combined:

retrieved_notes = "\n".join(results['documents'][0])

The result becomes one text block passed to the assessment engine.


9. No-history case
------------------

Before retrieval:

ehr_history = "NO PRIOR HOSPITAL HISTORY FOUND."

If no MRN exists, retrieval is skipped and this value remains.

If an MRN exists but no matching documents are found, the retrieval function
returns:

NO PRIOR HOSPITAL HISTORY FOUND. First-time walk-in patient.

The assessment prompt explicitly instructs:

If the EHR contains "NO PRIOR HOSPITAL HISTORY", evaluate strictly on current
vitals and complaint.

Interview answer:

"A missing history is represented explicitly with a sentinel message. This
prevents the LLM from confusing no records found with a retrieval bug or
inventing prior history."


10. Retrieval failure
---------------------

The retrieval is wrapped in try/except:

try:
    ...
except Exception as e:
    logger.error(f"RAG Retrieval Error: {e}")
    return "NO PRIOR HOSPITAL HISTORY FOUND."

If Chroma fails because of a database issue, embedding error, invalid query,
or configuration issue, the service logs the failure and returns a no-history
fallback.

This allows triage to continue using current vitals and complaint.

Important safety nuance:

The fallback does not distinguish:

1. The patient genuinely has no history.
2. The database was unavailable.

A production system should distinguish NOT_FOUND from RETRIEVAL_ERROR
internally, even if both are safe to show to a client.


11. Temporal trap
-----------------

The records include dates:

[DATE: Oct 2024]
[DATE: Jan 2021]

The older note says:

pregnancy. (RESOLVED)

The intended rule is:

"A temporary condition from an old note should not automatically be treated as
a current condition."

The prompt tells the LLM:

"If a retrieved note is dated over 9 months ago and involves a temporary
condition such as pregnancy or acute infection, treat it as resolved unless
current symptoms suggest otherwise."

Why this matters:

EHR history is not automatically current. A fact can be:

- Permanent, such as an allergy or past myocardial infarction
- Temporary, such as pregnancy, infection, or acute injury
- Time-dependent, such as blood pressure or medication use

Interview answer:

"RAG retrieves history, but retrieval does not mean every historical fact is
currently true. The temporal rule prevents an old temporary condition from
being treated as active without current supporting evidence."

Important implementation detail:

The temporal logic is currently expressed in the LLM prompt, not deterministic
code. The retrieval function does not parse dates, calculate age of notes,
identify temporary conditions, or remove stale notes.

Production critique:

"The temporal rule is prompt-based rather than enforced in code. That is
flexible, but less deterministic. For a safety-critical system, I would
extract note dates and condition types and apply a deterministic temporal policy
before or alongside LLM interpretation."


12. Contradictory clinical information
---------------------------------------

The prompt also includes:

"If the patient's dictated complaint contradicts documented allergies in the
EHR, prioritize the EHR as a clinical warning."

RAG can retrieve:

- Allergies
- Prior cardiac events
- Chronic illnesses
- Previous complications


13. How RAG connects to assessment
----------------------------------

The endpoint calls:

ehr_history = retrieve_patient_history(
    request.mrn,
    safe_complaint
)

Then:

assessment = execute_triage_assessment(
    patient=patient_dict,
    scrubbed_complaint=safe_complaint,
    ehr_history=ehr_history,
    routing=routing_info
)

The assessment prompt includes:

Vitals
Complaint: scrubbed_complaint
EHR: ehr_history

Division of responsibility:

XGBoost    -> numerical vitals and patient fields
ChromaDB   -> historical EHR documents
LLM        -> complaint, vitals, and retrieved EHR context
Confidence -> model output, missing data, routing

----------------

Matching patient:

{
  "mrn": "MRN-A3F9",
  "complaint": "Chest pressure and shortness of breath"
}

15. Strong technical interview answer for rag_engine.py
--------------------------------------------------------

"The RAG layer uses ChromaDB to store EHR notes as documents with MRN
metadata. When a patient is evaluated, the current complaint is used as a
semantic query so the system can find clinically related history even when the
wording is different.

At the same time, the query applies where={'mrn': mrn}. This is an exact
metadata filter, so only documents belonging to the current patient are
eligible. The complaint is the relevance signal, while the MRN is the identity
constraint. This prevents a semantically similar note from another patient
from entering the assessment.

The system retrieves up to three matching notes and combines them into one
history string. If there is no MRN or no matching record, it returns an
explicit no-history message and the assessment proceeds using current data
only.

The records include dates because old temporary conditions, such as a past
pregnancy or infection, should not automatically be treated as current. The
current implementation communicates that temporal rule to the LLM through the
prompt. For stronger safety, date parsing and temporal filtering could also be
implemented deterministically."


RAG follow-up questions
-----------------------

Q: What is the difference between semantic search and exact filtering?

A: Semantic search finds documents based on meaning and similarity. Exact
filtering enforces a strict condition such as metadata["mrn"] == requested_mrn.
Semantic search ranks relevance; exact filtering enforces identity.

Q: Why not search only by MRN?

A: Searching only by MRN would retrieve the patient's entire history without
ranking it by current relevance. Combining MRN filtering with complaint search
retrieves the most relevant subset.

Q: Why not search only by complaint?

A: That could return another patient's record with a similar complaint. It
creates a patient-data mixing risk.

Q: What happens when there is no history?

A: The system returns an explicit no-history string and instructs the
assessment layer to use the current complaint and vitals only.

Q: Is the temporal trap fully enforced?

A: Not deterministically. Retrieved notes contain dates, and the LLM prompt
explains how to treat old temporary conditions. A production system should
also apply programmatic date and condition logic.

Q: Does the current implementation persist EHR data?

A: It creates a standard Chroma client and seeds records at startup, but it
does not currently pass the configured persistence directory to Chroma. I
would verify persistence behavior and wire it explicitly for production.

Q: What is the most important security property?

A: The hard MRN metadata filter. It ensures semantic similarity cannot override
patient identity. The safe retrieval rule is: first restrict to the patient,
then rank by complaint relevance.


PART 4: backend/app/services/routing_engine.py
================================================

Interview-ready overview:

routing_engine.py chooses an age-based routing category:

- Pediatric
- Adult
- Geriatric

It does not itself perform the final triage assessment. It creates routing
metadata that is passed to the assessment engine.

The main idea is:

"Patient age determines which clinical baseline or model route should be used,
and uncertain age reduces confidence."


1. DOB to age calculation
-------------------------

The function is:

def calculate_age_years(dob: Optional[date]) -> float:
    if not dob:
        return -1.0

    today = date.today()
    return (today - dob).days / 365.25

It calculates age in years using an approximate 365.25 days per year.

The sentinel -1.0 means age is unknown.

Interview answer:

"The router calculates age from DOB. If DOB is missing, it returns a sentinel
value of -1.0 so the caller can enter the unknown-age flow."


2. Standard age groups
----------------------

Pediatric:

if age < 18.0:
    model_route = "PEDIATRIC_MODEL"

Adult:

18 <= age < 65

model_route = "ADULT_MODEL"

Geriatric:

if age >= 65.0:
    model_route = "GERIATRIC_MODEL"

Boundaries:

Age < 18        -> Pediatric
18 through <65  -> Adult
Age >= 65       -> Geriatric

Examples:

Age 5:

{
  "model_route": "PEDIATRIC_MODEL",
  "uncertainty_penalty": 0.0,
  "warning": null
}

Age 35:

{
  "model_route": "ADULT_MODEL",
  "uncertainty_penalty": 0.0,
  "warning": null
}

Age 70:

{
  "model_route": "GERIATRIC_MODEL",
  "uncertainty_penalty": 0.0,
  "warning": null
}


3. Unknown age flow
--------------------

If DOB is missing:

age = -1.0

Then:

if age == -1.0:
    estimated_group = patient_data.get(
        "estimated_age_group",
        "ADULT"
    )

The mapping is:

INFANT or CHILD -> PEDIATRIC_MODEL
SENIOR          -> GERIATRIC_MODEL
anything else   -> ADULT_MODEL

If no estimated group is supplied, the system defaults to adult.


4. 15 percent uncertainty penalty
----------------------------------

For unknown age, the router returns:

"uncertainty_penalty": 0.15

and:

"warning": "Age estimated. Clinical baselines may be inaccurate."

The assessment engine applies:

base_confidence -= routing_penalty * 100

So:

0.15 * 100 = 15 points

Example:

Initial ML confidence: 84
Unknown-age penalty: 15
Adjusted confidence: 69

This is a subtraction of 15 percentage points, not 15 percent of the
remaining score.

Interview answer:

"When age is estimated instead of known, the router adds a 0.15 penalty. The
assessment engine converts that to a 15-point reduction because age-specific
clinical baselines may be inaccurate."


5. How routing affects the rest of the system
----------------------------------------------

The routing result is passed to execute_triage_assessment().

It affects:

A. Confidence:

routing.get("uncertainty_penalty", 0.0)

B. Deterministic badges:

is_pediatric = routing.get("model_route") == "PEDIATRIC_MODEL"

Pediatric heart-rate rules:

hr > 180 -> Pediatric Tachycardia
hr < 160 -> Normal Ped HR

Adult/geriatric rules:

hr > 120 -> Tachycardia
60 <= hr <= 100 -> Normal HR


6. Important limitation: routing labels versus actual model
------------------------------------------------------------

The router returns labels:

PEDIATRIC_MODEL
ADULT_MODEL
GERIATRIC_MODEL

However, assessment_engine.py loads only one XGBoost model:

triage_model = joblib.load(MODEL_PATH)

The inference function does not select a model based on routing["model_route"].
It always calls:

triage_model.predict_proba(features)

Therefore:

"Routing says which age-specific route should be used, but inference still uses
one shared XGBoost artifact."

The route is currently used for:

- Reporting
- Confidence penalties
- Age-aware badges

It is not selecting three separate trained models.

Strong interview answer:

"The routing engine is designed to support stratified models, but the current
assessment engine loads one XGBoost model. Therefore, the route labels are
currently metadata and policy signals rather than actual model selection. To
implement true stratified inference, I would load separate pediatric, adult,
and geriatric artifacts or use one model with a validated age-aware
preprocessing strategy."


7. Relationship to XGBoost features
------------------------------------

Age is still an input feature:

age, hr, bpSys, bpDia, spo2, temp, pain, MRN/history flag

But routing does not change the feature vector or model object.

Important distinction:

Age is a model input.
Age route is not currently a model selector.


8. DOB type limitation
----------------------

triage.py currently declares:

dob: Optional[str] = None

but calculate_age_years() expects:

dob: Optional[date]

and performs:

today - dob

If dob remains a string at runtime, subtraction can raise a type error.

A consistent request definition would be:

from datetime import date
dob: Optional[date] = None

Then Pydantic can parse an ISO date such as:

{
  "dob": "1990-04-12"
}

into a Python date.


9. The explicit age field is not used by routing
------------------------------------------------

TriageRequest also has:

age: Optional[float] = None

But routing calculates age from:

It does not fall back to patient_data.get("age").

Therefore:

{
  "age": 70,
  "dob": null
}

does not automatically route to geriatric. It enters the unknown-age flow and
defaults to adult unless estimated_age_group is supplied.

Interview observation:

"The schema accepts both age and DOB, but routing currently gives precedence to
DOB and does not use the explicit age field when DOB is absent. I would define
one canonical source or add a clear fallback from DOB to age."

"The routing engine calculates age from DOB using the current date and an

PART 5: backend/app/middleware/pii_scrubber.py
================================================

Interview-ready overview:

pii_scrubber.py is intended to remove personally identifiable information from
the patient complaint before the text is sent to retrieval or the LLM.

Important distinction:

"The documentation describes a broader enterprise PII scrubber, but the
current implementation only performs patient-name replacement and phone-number
replacement. It does not currently implement complete PII detection."


1. scrub_pii()
---------------

Function:

def scrub_pii(text: str, patient_name: Optional[str] = None) -> str:

Inputs:

- text: complaint text
- patient_name: known patient name, if available

Output:

- cleaned text

Endpoint call:

safe_complaint = scrub_pii(request.complaint, request.name)


2. Patient-name removal
-----------------------

The code:

if patient_name:
    pattern = re.compile(
        re.escape(patient_name),
        re.IGNORECASE
    )
    scrubbed_text = pattern.sub(
        "[PATIENT_NAME]",
        scrubbed_text
    )

The replacement is case-insensitive.

Raw:

John Doe has severe chest pain

Scrubbed:

[PATIENT_NAME] has severe chest pain

re.escape() treats the name as literal text rather than a regular expression.

Limitations:

- Only the supplied patient name is removed.
- Other people's names are not necessarily removed.
- Misspellings and nicknames are not necessarily removed.


3. Phone-number regex
----------------------

The actual implemented regex is:

phone_pattern = r'\(?\d{3}\)?[-.\s]?\d{3}[-.\s]?\d{4}'

It is used with:

scrubbed_text = re.sub(phone_pattern, "[PHONE]", scrubbed_text)

Designed examples:

123-456-7890
(123) 456-7890
123.456.7890
123 456 7890
1234567890

Example:

Call John Doe at 555-123-4567 about chest pain

becomes:

Call [PATIENT_NAME] at [PHONE] about chest pain

Limitations:

- It may match numbers that are not phone numbers.
- It may miss international formats.
- It may miss extensions.
- It may miss unusual formatting.
- It could match a 10-digit identifier that looks like a phone number.

6. Fail-closed behavior
------------------------

The function is wrapped in try/except:

try:
    ...
except Exception as e:
    logger.error(
        f"PII Scrubber failed: {str(e)}. "
        "Triggering Fail-Closed protocol."
    )
    return (
        "[SYSTEM ERROR: PII SCRUBBER FAILED. "
        "TEXT WITHHELD FOR HIPAA COMPLIANCE.]"
    )

If scrubbing raises an exception:

1. The error is logged.
2. The original text is not returned.
3. A withholding message is returned.

Fail-open:

Scrubber fails -> send original text anyway.

Fail-closed:

Scrubber fails -> do not release original text.

Interview answer:

"The scrubber fails closed because returning raw complaint text after a
privacy-processing error could leak patient information to downstream AI
services. The safer behavior is to withhold the text."


7. Why scrub before LLM ingestion?
-----------------------------------

Raw:

John Doe, phone 555-123-4567, reports chest pain

LLM input:

[PATIENT_NAME], [PHONE], reports chest pain

The clinical meaning is preserved while direct identifiers are reduced.

The scrubber creates a boundary between:

Raw patient input

and:

External or downstream AI processing

Interview answer:

"PII is scrubbed before LLM ingestion because the LLM needs the clinical facts,
not the patient's identity. This reduces unnecessary exposure of sensitive data
and supports data-minimization principles."


8. How it affects RAG
----------------------

The endpoint passes the scrubbed complaint to RAG:

ehr_history = retrieve_patient_history(
    request.mrn,
    safe_complaint
)

Benefits:

1. The LLM does not receive raw identifiers through the complaint.
2. The vector query is based more on clinical meaning than personal identity.

The MRN is used separately for exact metadata filtering. The scrubber does not
remove the MRN from the request object; it only processes complaint text.


9. What is and is not scrubbed
------------------------------

Scrubbed:

request.complaint -> safe_complaint

Used by:

- Semantic EHR retrieval
- LLM assessment prompt

Not scrubbed by this function:

- request.mrn
- request.name as a separate field
- patient_dict
- EHR documents already stored in ChromaDB
- Other arbitrary request fields

The name remains in patient_dict, but XGBoost only extracts numeric fields and
the assessment prompt uses scrubbed_complaint rather than the raw name field.

Important security wording:

"The scrubber protects the complaint text path. It is not a general-purpose
sanitizer for the entire request or database."


10. Strong technical interview answer for pii_scrubber.py
----------------------------------------------------------

"The PII scrubber runs before the complaint reaches the RAG and LLM layers. It
receives the complaint and the known patient name, replaces the name
case-insensitively with [PATIENT_NAME], and uses a regular expression to
replace phone-number-like values with [PHONE].

The function is fail-closed: if scrubbing raises an exception, it logs the
failure and returns a text-withheld message instead of returning the original
complaint. This prevents raw patient text from being sent downstream after a
privacy-processing failure.

A medical whitelist is declared for terms such as Parkinson and Crohn, but the
current loop only contains pass, so the whitelist is not actually doing
anything. Also, although the comments mention SSNs and dates, the current code
does not implement regexes for them.

Therefore, the accurate description is that this is a basic name-and-phone
scrubber with fail-closed behavior, not a complete enterprise PII detection
system."


PII follow-up questions
-----------------------

Q: What PII does it actually remove?

A: The supplied patient name and phone-number-like patterns. It does not
currently remove SSNs, dates of birth, emails, addresses, or MRNs from
arbitrary text.

Q: Does the medical whitelist work?

A: No. It is declared but not applied. The loop uses pass, so it has no
runtime effect.

Q: Why fail closed?

A: If privacy processing fails, sending the original text onward could expose
PII. Returning a withholding message is safer.

Q: Does it scrub the MRN?

A: Not through this function. The MRN is passed separately to RAG as an exact
metadata filter. It is not included in the complaint text being scrubbed.

Q: Could the phone regex have false positives?

A: Yes. It is a simple pattern and could match a non-phone 10-digit value or
miss international and unusual formats.

Q: What would you improve?

A: I would implement a complete, tested PII strategy for names, phone numbers,
emails, dates of birth, addresses, SSNs, and identifiers; make the whitelist
functional; add tests for false positives and formatting variations; avoid
logging sensitive exception content; and return structured scrubber status so
downstream code can distinguish normal text from withheld text.

Q: Is the current scrubber enough for HIPAA compliance?

A: I would not make that claim. It provides a useful privacy layer, but it is
not comprehensive enough by itself to guarantee removal of all protected health
information.

4. Target ESI generation
-------------------------

The target is generated with deterministic rules.

ESI 1:

if sp < 82 or s <= 65 or h < 35:
    esi.append(1)

Represents extreme instability such as severe hypoxia, severe hypotension, or
extremely low heart rate.

ESI 2:

elif sp <= 92 or s < 88 or h > 135 or (a <= 0.25 and t >= 38.0) or (a >= 65 and s < 95 and h > 110):
    esi.append(2)

Represents high-risk or emergent cases such as significant hypoxia, low
systolic pressure, severe tachycardia, fever in a very young infant, or
concerning vitals in an older patient.

ESI 3:

elif h > 105 or s > 165 or t >= 38.5 or (p >= 7 and (hx == 1 or a > 50)):
    esi.append(3)

Represents urgent cases such as moderate tachycardia, high blood pressure,
high fever, or severe pain with additional risk context.

ESI 4:

elif p >= 4 or t > 37.8 or hx == 1:
    esi.append(4)

Represents semi-urgent cases.

ESI 5:

else:
    esi.append(5)

Represents stable or non-urgent cases.


5. Target encoding
------------------

The script converts clinical ESI labels to zero-based classes:

"esi": [e - 1 for e in esi]

Mapping:

Clinical ESI 1 -> model class 0
Clinical ESI 2 -> model class 1
Clinical ESI 3 -> model class 2
Clinical ESI 4 -> model class 3
Clinical ESI 5 -> model class 4

At inference time:

predicted_esi = top_class_idx + 1

Interview answer:

"The target is a five-class classification problem. Training uses zero-based
labels, and inference converts the result back to clinical ESI 1 through 5."

11. Precision
-------------

Precision answers:

"When the model predicts a particular class, how often is that prediction
correct?"

Formula:

Precision = True Positives / (True Positives + False Positives)

For ESI 1:

Precision = correctly predicted ESI 1 cases /
            all cases predicted as ESI 1

ESI 1 precision is 1.00, meaning every case predicted as ESI 1 was actually
ESI 1 in this test run.

High precision means fewer false alarms for that class, but it does not mean
the model found every actual case.


12. Recall
-----------

Recall answers:

"Of all patients who truly belong to a class, how many did the model find?"

Formula:

Recall = True Positives / (True Positives + False Negatives)

ESI 1 recall is 0.93. With 28 true ESI 1 cases, the model detected
approximately 26 and missed approximately 2.

For high-acuity triage, recall is especially important because a false negative
can under-triage a critically ill patient.

Interview answer:

"Recall measures how many actual members of a class were successfully
identified. ESI 1 recall was 93 percent, so the model did not identify every
true ESI 1 case. In a clinical system, those false negatives would require
careful investigation."


13. F1 score
------------

F1 is the harmonic mean of precision and recall:

F1 = 2 * (Precision * Recall) / (Precision + Recall)

For ESI 1:

Precision = 1.00
Recall = 0.93
F1 = 0.96

F1 is high only when both precision and recall are high. The harmonic mean
penalizes imbalance between them.

Interview answer:

"F1 balances precision and recall. It is useful when we want a single score
that reflects both false positives and false negatives."

17. Is 99 percent accuracy realistic?
--------------------------------------

does not validate clinical performance in the real world."

Training and metric follow-up questions
----------------------------------------

Q: What is the difference between precision and recall?

A: Precision asks, "When the model predicts this class, how often is it
correct?" Recall asks, "Of all actual cases in this class, how many did the
model find?"

Q: Which is more important for triage?

A: It depends on the class and objective, but recall for high-acuity ESI 1 and
ESI 2 cases is especially important because false negatives can cause
under-triage.

Q: Why is F1 useful?

A: F1 combines precision and recall into one score and is useful when both
false positives and false negatives matter.

Q: Why report macro and weighted averages?

A: Macro average gives every class equal importance. Weighted average accounts
for the number of samples in each class. With imbalanced data, both provide
different useful perspectives.

Q: Can you trust the 99 percent accuracy?

A: I can trust it as a measurement on this exact synthetic test split, but not
as a claim about real clinical accuracy. The dataset is synthetic, rule-labeled,
and generated from the same features used by the model.

Q: Could this be overfitting?

A: It may not be classic train/test overfitting because the test set is
separate, but the evaluation is still optimistic because the test data follows
the same synthetic rules and distributions as the training data. I would use
cross-validation and an independent real-world validation set.

Q: Why use stratification?

A: It preserves the class distribution in both train and test sets, which is
important because ESI classes are imbalanced.

Q: What does support mean?

A: Support is the number of true examples of a class in the test set. ESI 1
had support of 28.

Q: What would you improve?

A: I would add cross-validation, a confusion matrix, calibration analysis,
class-specific under-triage metrics, external validation on expert-labeled
data, and subgroup analysis. I would also version the dataset, feature schema,
model artifact, and training configuration.

Q: Is the model production-ready?

A: Not based on this evaluation alone. It is a useful prototype model, but
clinical deployment would require expert-reviewed labels, external validation,
calibration, safety review, monitoring, and human oversight.


FINAL ONE-MINUTE SYSTEM EXPLANATION
====================================

"The system accepts a validated triage request through FastAPI. The complaint
is scrubbed for direct identifiers before it is used by the retrieval and LLM
layers. The patient is routed into pediatric, adult, or geriatric categories
based on DOB, with a 15-point confidence penalty when age must be estimated.

For patients with an MRN, ChromaDB performs semantic search over EHR history
using the complaint, but hard-filters by MRN. The complaint determines
relevance, while the MRN guarantees patient identity and prevents similar
records from another patient being mixed into the assessment.

The assessment engine creates an eight-feature vector and sends it to a
five-class XGBoost model. The model returns probabilities for ESI 1 through 5,
and the highest class is converted from a zero-based index to a clinical ESI
number. The top probability becomes the starting confidence, and the margin
between the top two classes measures certainty.

An LLM separately interprets the complaint and retrieved history and returns a
category, ESI, and rationale in JSON. The system compares the LLM and ML ESI
values. Agreement can provide a small margin-based confidence bonus, while
disagreement reduces confidence by 15 points. Missing high-value vitals cause
additional context-specific penalties.

Deterministic rules generate badges for findings such as hypoxia,
hypotension, hypertension, and tachycardia. If the LLM or model fails, the
system falls back to the XGBoost result and explains that it is operating in
fallback mode.

The XGBoost model came from a training script that generated 5,000 synthetic
records and rule-based ESI labels. It achieved approximately 99 percent
accuracy on the synthetic test split, with 98 percent macro F1 and 99 percent
weighted F1. Those results show that the prototype learned the synthetic
labeling policy, but they do not establish real-world clinical accuracy."


MOST IMPORTANT LIMITATIONS TO REMEMBER
=======================================

1. The training data is synthetic and labels are generated from the same
   features used by the model, so the 99 percent accuracy is optimistic.

2. The routing engine labels pediatric, adult, and geriatric routes, but the
   assessment engine currently loads one shared XGBoost model.

3. The request declares DOB as Optional[str], while routing expects a date.

4. Routing uses DOB but does not fall back to the separate age field.

5. Missing model features receive normal-looking defaults, which can hide
   whether a vital was actually measured.

6. LLM JSON is parsed but not validated against a schema.

7. ML/LLM disagreement reduces confidence, but there is no explicit policy for
   choosing the safer ESI.

8. The temporal-trap rule is prompt-based, not deterministic date processing.

9. ChromaDB is created with a standard client, while the configured persistence
   directory is not currently wired into the client.

10. The PII scrubber actually removes only the supplied name and phone-like
    values. The SSN/date comments and medical whitelist are not implemented.

11. The endpoint catches all exceptions and exposes str(e), which may leak
    internal details.

12. The fallback ESI values are fixed prototype behavior and should not be
    treated as a complete clinical safety policy.
